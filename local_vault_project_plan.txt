Below is a practical implementation plan for **Local Vault using JavaScript instead of TypeScript**.

## 1. Project goal

Build an offline-first encrypted knowledge vault that supports:

- journals
- notes
- code snippets
- encrypted local storage
- fast local search
- encrypted backup and restore
- PDF/Markdown/JSON export
- automatic locking
- PWA installation
- attachments
- revision history

The application should have **no backend dependency** and should not require user accounts.

---

# 7. Phase 2 — IndexedDB

Use Dexie.

Example:

```javascript
import Dexie from "dexie";

export const db = new Dexie("LocalVault");

db.version(1).stores({
  vault: "id",
  items: "id, type, createdAt, updatedAt",
  attachments: "id, itemId",
  settings: "key",
});
```

Your initial database could contain four primary tables.

```text
vault
items
attachments
settings
```

Do not create separate note/journal/snippet tables initially.

Use one generic `items` table.

# 8. Generic item model

JavaScript does not provide TypeScript interfaces, so document object structures with JSDoc.

```javascript
/**
 * @typedef {Object} VaultItem
 * @property {string} id
 * @property {"note"|"journal"|"snippet"} type
 * @property {number} createdAt
 * @property {number} updatedAt
 * @property {number} cryptoVersion
 * @property {Uint8Array} iv
 * @property {ArrayBuffer} ciphertext
 */
```

This gives you some editor autocomplete and documentation without TypeScript.

# 9. Phase 3 — Vault encryption

This is the most important phase.

Do not encrypt notes directly with the user's password.

Use:

```text
Password
   ↓
PBKDF2
   ↓
Key Encryption Key
   ↓
Decrypt master key
   ↓
Master Vault Key
   ↓
Encrypt vault data
```

When creating a vault:

```text
Generate random master key
        ↓
User chooses password
        ↓
Generate random salt
        ↓
PBKDF2(password, salt)
        ↓
Create key-encryption key
        ↓
Encrypt master key
        ↓
Store encrypted master key
```

---

# 10. Generate the master key

Using Web Crypto:

```javascript
async function createMasterKey() {
  return crypto.subtle.generateKey(
    {
      name: "AES-GCM",
      length: 256,
    },
    true,
    ["encrypt", "decrypt"]
  );
}
```

---

# 11. Derive a key from password

Conceptually:

```javascript
async function deriveKey(password, salt) {
  const encoder = new TextEncoder();

  const passwordKey = await crypto.subtle.importKey(
    "raw",
    encoder.encode(password),
    "PBKDF2",
    false,
    ["deriveKey"]
  );

  return crypto.subtle.deriveKey(
    {
      name: "PBKDF2",
      salt,
      iterations: 300000,
      hash: "SHA-256",
    },
    passwordKey,
    {
      name: "AES-GCM",
      length: 256,
    },
    false,
    ["encrypt", "decrypt"]
  );
}
```

The exact iteration count should eventually be benchmarked rather than hardcoded arbitrarily.

---

# 12. Encrypted database record

Instead of:

```javascript
{
  title: "Secret API notes",
  content: "...",
  tags: ["work"]
}
```

IndexedDB should see something resembling:

```javascript
{
  id: "item_123",
  type: "note",
  cryptoVersion: 1,
  iv: Uint8Array(...),
  ciphertext: ArrayBuffer(...),
  createdAt: 1780000000000,
  updatedAt: 1780000000000
}
```

Inside the encrypted payload:

```javascript
{
  title: "Secret API notes",
  content: "...",
  tags: ["work"],
  favorite: false
}
```

Therefore titles and tags are not exposed in IndexedDB.

# 13. Crypto service

Create:

```text
src/services/crypto.service.js
```

The public API should look approximately like:

```javascript
export async function createVault(password) {}

export async function unlockVault(password) {}

export async function lockVault() {}

export async function encryptObject(data, key) {}

export async function decryptObject(record, key) {}

export async function changeVaultPassword(
  oldPassword,
  newPassword
) {}
```

Other parts of the application should not need to understand Web Crypto directly.

# 14. Vault state

Keep the unlocked master key only in memory.

Example Zustand store:

```javascript
import { create } from "zustand";

export const useVaultStore = create((set) => ({
  status: "locked",
  masterKey: null,

  unlock(masterKey) {
    set({
      status: "unlocked",
      masterKey,
    });
  },

  lock() {
    set({
      status: "locked",
      masterKey: null,
    });
  },
}));
```

Do not put the master key into:

```text
localStorage
sessionStorage
IndexedDB
cookies
```

The persisted copy should remain encrypted.

# 25. Phase 6 — Backup

This should be completed before attachments or advanced exports.

Create your own format:

```text
my-vault.lvault
```

The extension can simply represent a structured encrypted file.

Conceptually:

```javascript
{
  format: "local-vault",
  version: 1,
  createdAt: "...",
  vault: {},
  items: [],
  attachments: []
}
```

All sensitive payloads remain encrypted.

# 32. Password changes

Because the master-key architecture is being used:

```text
Old password
    ↓
decrypt master key

New password
    ↓
derive new wrapping key
    ↓
encrypt same master key
```

You do not need to decrypt and re-encrypt thousands of notes.

This is one major advantage of the master-key design.

---

# 33. PWA support

After the core vault is stable, turn the application into a PWA.

Cache only application resources:

```text
HTML
CSS
JavaScript
icons
fonts
```

Do not cache decrypted content.

User data belongs in encrypted IndexedDB.

---

# 34. Avoid remote resources

For a privacy-oriented application, bundle dependencies.

Avoid:

```text
Google Fonts
CDN JavaScript
remote syntax themes
analytics
tracking pixels
remote error logging containing content
```

The application should still work if the computer has no network access.

---

# 35. Content Security Policy

Eventually use a restrictive CSP.

Conceptually:

```text
default-src 'self'
script-src 'self'
style-src 'self'
img-src 'self' blob: data:
connect-src 'none'
```

Development mode will require exceptions, but production should be strict.

The especially interesting rule is:

```text
connect-src 'none'
```

for a truly network-independent deployment.

# 42. Testing strategy

The crypto system should receive significantly more testing than the UI.

Test:

```text
encrypt → decrypt
incorrect password
corrupted ciphertext
different IVs
backup → restore
password changes
database migrations
deleted records
search rebuilding
vault locking
```

A critical test might be:

```javascript
it("restores the original note after encryption", async () => {
  const original = {
    title: "Test",
    content: "Secret data",
  };

  const encrypted = await encryptObject(original, key);
  const decrypted = await decryptObject(encrypted, key);

  expect(decrypted).toEqual(original);
});
```

# 43. Database migrations

Plan for database changes immediately.

Example:

```javascript
db.version(1).stores({
  items: "id,type,createdAt",
});

db.version(2).stores({
  items: "id,type,createdAt,updatedAt",
```

Never assume your first database design will remain permanent.

# 44. Crypto versioning

Every encrypted record should contain:

```javascript
cryptoVersion: 1
```

Later you may introduce:

```javascript
cryptoVersion: 2
```

This lets you migrate encryption schemes without breaking old vaults.

# 45. Error strategy

Define application-specific errors.

Example:

```javascript
export class VaultLockedError extends Error {}

export class InvalidPasswordError extends Error {}

export class CorruptedVaultError extends Error {}

export class UnsupportedBackupVersionError extends Error {}
```

Then UI components can show meaningful messages rather than cryptographic errors.

---

# 46. Do not log sensitive information

Avoid:

```javascript
console.log(note);
console.log(masterKey);
console.log(decryptedData);
```

Even development logs can leak information.

Implement safe logging.

```javascript
console.debug("Note saved", {
  id: note.id,
});
```

Not:

```javascript
console.debug(note);
```
